# 覆盖设计与工具选择

## 从真实资料建立覆盖分母

先收集需求、源文件、资源表、历史缺陷和用户确认的范围，再设计测试。保留来源版本/指纹。不能只阅读实现中已经支持的类别，否则未实现的需求会消失在清单外。

建立四类覆盖项，每项都有稳定 ID、预期和必须通过的用例 ID：

| 类型 | 分母如何确定 | 通过依据 |
|---|---|---|
| requirement | 当前已确认的业务要求 | 对应可观察行为全部符合预期 |
| resource | 资料盘点的类别 × 当前要求的状态/面向 | 每个应支持关系在适当场景完整可见且映射正确 |
| combination | 重要完整场景、对象间关系和已知缺陷 | 应出现的对象、数量、范围、遮挡等整体关系正确 |
| workflow | 实际用户操作路径 | 从输入到结果、更新、取消及持久化的适用步骤正确 |

用例可以关联多个覆盖项，但一个覆盖项的所有必需用例都通过才计入通过分子。诊断用例不作为产品验收用例。暂缓/不适用保留在清单并写用户决定或适用理由；实现漏项、缺资源、环境不足不能擅自改为暂缓。没有分母时写“已覆盖 N 项，完整性未知”，不写“100%”。代码行/分支覆盖需专门工具测量，不能从断言数推算。

## 参数与组合

- 先列实际对象/资源类别、方向/状态、位置、尺寸/深度等输入维度及有效约束，再列正常值、最小/最大/阈值内外、异常值和取消行为。
- 连续取值用业务等价类和边界覆盖；不存在可诚实宣称的“全量所有坐标”。类别有限且可盘点时枚举全部，重要交互关系和历史失败组合必须单列。低风险独立维度可用成对组合压缩，记录依据和余留风险。
- 正常场景不能全是独立单对象；必须有来自真实资料的完整组合。逐类独立通过后，还要核对组合中的相对位置、重复实例、遮挡、裁切及漏项。
- 编写预期时记录独立来源与可核对数量/几何/可见性；视觉场景先准备原图或示意对照。不能从插件输出复制期望值。
- “全量”指本轮声明的有限覆盖清单，报告同时列未盘点、未测、失败和暂缓。原图包含暂缓能力时，说明与原图的差距，不能把范围内通过写成原图完全复现。

## 实操主线与脚本补充

执行顺序通常是：盘点/计划 → 短预检 → 桌面实操 → 数值核对和回归 → 必要修复与实操复测 → 交付。可按失败定位调整，但切换方式要先通知。

真实 UI 验收从软件通常的打开方式、实际面板/按钮、点选/捕捉等路径出发，保存全景、关键局部及必要中间状态。截图必须实际查看并说明比较结论，不能只检查文件存在。由驱动输入仍属于实操，前提是经过真实 UI 和独立结果核对；内部 API 直接调用只计其本身层次。

脚本可以准备测试副本、输出精确对象清单、核对数量/坐标、枚举大量边界并快速回归。准备步骤若绕过了需要验收的创建或设置过程，不得把该用例算作该交互路径已测。脚本执行多不是问题，不能用它掩盖必须实操的未测项。

## 覆盖分层

| 层次 | 验证内容 | 对办公桌面的要求 |
|---|---|---|
| 算法与业务单元 | 正常、边界、异常、数值误差、幂等性、数据转换 | 通常无需窗口 |
| 真实服务或宿主 | 命令、存储、事务、插件加载、保存重开、原生撤销 | 选官方 CLI/API/无界面宿主；核查实际启动行为 |
| 控件与窗口集成 | 绑定、事件、对话框、命令路由 | 取决于框架和控件；单列入口，先验证是否抢焦点 |
| 真实输入与视觉 | 点击命中、快捷键、拖拽、捕捉、DPI、遮挡、焦点、实际渲染 | 使用独立测试机或虚拟机可与用户办公并行；否则安排明确的桌面占用时段 |

只调用按钮处理函数只能证明该函数路径。通过数据库检查只能证明相应数据条件。导出图像后还需实际查看或用独立指标比较，才能支持视觉结论。涉及真实 GPU、设备驱动或硬件授权时，应核对隔离环境是否能代表用户环境。

## 在现有项目中落地

保留现有解决方案与业务项目。把调度脚本、测试夹具、断言和报告放进已有验证工程；缺乏此结构时再建立清晰的验证目录。在已有 README 写明后台入口、需授权的桌面入口、所需环境及未测范围，不强制另建一套框架。

默认入口不得隐式转向完整 GUI 或屏幕驱动。屏幕入口使用显式启用参数，指向本轮创建的测试实例，核对 PID、启动时间或相应进程身份；COM/UIA 返回的实例也要与目标匹配。不要任取同名进程或借用用户正在工作的文档。

选择开源工具时按技术栈和现有依赖判断：

- .NET 单元与集成测试可用 [NUnit](https://github.com/nunit/nunit) 等成熟框架；已有断言有效时无需仅为形式迁移。
- Windows 控件测试可评估 [FlaUI](https://github.com/FlaUI/FlaUI)（UIA2/UIA3）。先实测自定义绘图控件、权限和焦点行为，不能据 UIA 名称承诺任意应用后台操作。
- 跨工具报告可参照 [JUnit XML 结构说明](https://github.com/testmoapp/junitxml)，分别表达 failure、error、skipped；团队已有报告格式时优先兼容。
- AutoCAD 真实无界面宿主参考 [AcCoreConsole 示例](https://github.com/MadhukarMoogala/aps-da-for-autocad)，具体适用条件见 CAD 示例。

这些来源曾用于分层设计，并不代表框架已集成。2026-10-29 的报告与操作检查设计依据见 [开源借鉴](sources.md)。真正引入依赖前，再查当前版本、维护状态、许可证、平台支持和兼容性，不将搜索排名、星数或摘要当成质量与覆盖保证。

## 结果和资源

- 每轮唯一目录、独立环境和临时数据；记录输入指纹、提交及工作区改动、程序集/构建产物指纹、启动参数、工具版本、开始结束时间、各步骤状态。不能只记提交号而漏掉未提交改动。
- 输入和产物发生变化后，先判断受影响套件，补必要验证；历史报告需要重新匹配指纹和测试配置。没有相应指纹时不要声称证明了当前代码。
- 同时检查退出码、标准输出/错误及结构化报告。报告缺失、截断、重复终止标志、零断言、计数不符、失败断言、超时或资源超限均不是通过。空测试套件和主动跳过须明确记录为 NotRun/skipped。
- 采用 Passed、Failed、NotRun、Blocked、Error，报告失败原因与未测理由；被阻塞不等于通过。执行器自身错误保留为 Error，汇总不能仍为 Passed。用例 ID 稳定，每次尝试另有 ID，重试保留失败记录；构建/输入变化新建一轮。状态细则见报告规范。
- 优先串行、低优先级、可配置的步骤超时及内存保留。启动下一步骤前检查资源；缺资源则停止或拆分套件，不能以关闭办公程序腾资源。共享构建目录需要锁或独立输出；最终校验产物没有被其他构建替换。
- 调度器改动需验证失败传播、超时、环境隔离、报告拒收及清理边界。只增加与实际风险相关的检查，不为每个简单可逆编辑建立镜像测试。
- Windows PowerShell 5.1 的 `Get-Content` 字符串可能携带 Provider 扩展属性，直接 JSON 序列化会膨胀；需要纯文本报告时使用 `[IO.File]::ReadAllText` 或 `ReadAllLines`，并验证实际支持的 PowerShell 版本。

若软件完全没有可用的无界面接口，不强行宣称“全后台”。可以先提取可独立验证的业务逻辑，其余桌面任务在隔离环境执行，并保留端到端交互验收。
