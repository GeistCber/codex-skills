# 可控实操验收与自动化补充

桌面软件的交付验收以真实业务资料、完整界面操作和独立预期对照为主；脚本用于短预检、精确核对、定位和回归。实操可以由 AI 驱动鼠标键盘，但必须可知、可暂停、范围明确。保留技能名和既有命令以兼容现有配置。

验收单位是用户本次要求的**功能及其受影响流程**。按 [功能级验收](references/functional-acceptance.md) 确定范围、逐例检查点和影响边界；不用每次小改都验收整个软件，也不将某道实践题的参数、用例数或缺陷固定为通用要求。

## 开关与适用范围

- 本机配置：`C:\Users\Laptop\.codex\config.toml`，匹配路径为 `C:\Users\Laptop\.codex\skills\background-testing\SKILL.md` 的 `[[skills.config]]` 项。`enabled = false` 时跳过自动模式，不直接读取正文绕过关闭；缺项沿用默认启用。配置损坏或匹配项重复时停止自动模式并说明原因。
- 独立入口：[开启](../background-testing-on/SKILL.md)、[关闭](../background-testing-off/SKILL.md)。修改开关仅用编辑工具，回读确认，不用脚本重写配置。引用命令、讨论技能或查询状态不改变开关。
- 只读查询可运行 `python <本技能目录>/scripts/status.py`，仅输出本开关的 JSON。Python 需 3.11+；不可用时直接只读检查 TOML，不为查询安装依赖。
- 开启后在相关桌面项目开发和验收任务中采用本方法；纯问答、技能安装/修改和无关项目不触发业务测试。先前暂停或取消的工作不因开启而恢复。
- 状态跨会话保持。它是任务执行策略，不是常驻服务或定时监控；没有新任务或对话执行机会时不会自行唤醒。
- 用户在关闭状态下明确要求单次普通测试时，按该请求执行，不偷偷开启持久模式。对开关的明确操作交由独立入口处理。

## 执行主线

1. **盘点。** 从会话业务请求和实际文件定位项目，读取适用规则。盘点需求、真实输入、资源类别、面向/状态及已有缺陷；cwd 和本技能示例不能单独确定目标。先确定当前实现范围和明确暂缓项。
2. **建立覆盖计划。** 按 [测试方法](references/testing-method.md) 建立适用的需求、资源、完整场景组合、工作流清单和明确分母。逐例写可核对的对象、数量、几何/状态及来源，列参数等价类、边界和关键组合。新轮使用报告的 `functional-v1` 配置，执行前冻结计划；改变标准需新轮或明确修订，不能回填标准消除失败。
3. **短预检与桌面约定。** 后台先检查能否构建、加载及使用测试副本，避免占用桌面后才发现前提不成立。按 [桌面控制与生命周期](references/desktop-control.md) 声明阶段、目标和占用方式；已有具体授权直接沿用并通知，缺少桌面授权时一次集中确认，不反复询问。
4. **真实全流程验收。** 按业务用户实际路径完成操作，逐组检查输入状态、完整结果及关键局部，截图并与原始资料对照。包括正常、边界、异常/取消及保存重开等适用路径。不能用内部命令调用代替按钮、捕捉或拖拽的实操结论。AutoCAD 另读 [CAD 示例](references/autocad.md)。
5. **自动化补充与修复闭环。** 用算法、CLI/API、数据库或官方无界面宿主精确核对数据、定位差异和回归。问题出现后保留失败，区分产品、环境、测试前提和驱动问题；授权范围内修复后重测失败路径及受影响完整场景。业务构建或输入变化后新建运行记录，不拼接旧成功宣称当前版本全部通过。
6. **归档和释放。** 按 [报告规范](references/reporting.md) 交付覆盖矩阵、逐例预期/实际/截图、失败与未测项。桌面操作结束立即通知已释放；如仍有后台检查，说明正在做什么。最终分别报告实操与脚本结论、范围限制和报告路径。

“实操为主”是交付证据优先级，不要求每次小改都重跑整套。仅改纯算法时可先做针对性脚本回归；交付时复用证据必须匹配输入、构建和配置，并标明历史。没有 GUI 的项目沿用合适的脚本/API 测试，不制造无意义的鼠标操作。

## 桌面可控性

- 每次从后台进入桌面、从桌面返回后台、暂停、恢复和结束前，先通知当前阶段、已完成/待完成、下一步及是否占用鼠标键盘；通知不能代替尚未取得的授权。
- 启用技能不等于授权接管桌面。同一任务已授权的具体范围无需再次确认；越出目标应用/文件/操作范围才重新确认。用户要继续办公时，可先做补充脚本，实操保持待验收；或使用已授权的独立测试机/虚拟机。
- 仅对已核实身份的测试实例执行有限批次操作；每批前后观察目标状态。失焦、用户插入操作、未知弹窗、超时或异常时停止后续输入，释放已按住的键/鼠标并报告，不盲点、不无限重试、不反复抢回焦点。
- 通知和授权是执行约定，并非操作系统级隔离。驱动不能核验目标或不能及时停止时，缩小到可观察的单步操作或改为用户协助；不要承诺绝对不干扰办公。

## 报告与复用

以 `run.json` 为单一事实记录，图片、原始日志和参考资料放在同轮目录；从它生成 `report.md`，视觉密集的桌面验收同时生成离线 `report.html`。JSON 便于 AI 续接和工具核对，Markdown 便于检索/版本审阅，HTML 便于看图和筛选；不手工维护三套结论。首页分别显示无失败重试的通过、重试后通过、失败和未测；逐例展示检查点预期/实际/差异。历史证据保留来源和版本，不冒充本轮实跑。

可复用现有项目报告，只需满足规范；无需迁移框架。没有合适工具时可用本技能的标准库脚本：

```text
python <技能目录>/scripts/report.py <本轮目录>/run.json
python <技能目录>/scripts/report.py <本轮目录>/run.json --check
```

示例：[演示数据](assets/report-example/run.json)。示例不是业务测试证据。生成成功只证明报告有效，不证明产品通过；需要验收退出码时使用 `--require-pass`。字段及状态规则见报告规范。

可选工具：`scripts/session.py` 冻结计划并记录已发送的阶段通知；`scripts/desktop_guard.py` 为适配后的 Windows 驱动提供逐原子输入检查。它们不代替聊天通知、授权或项目的文档/控件状态判断，也不监控用户的全局输入。已有驱动可保留，先演练暂停、恢复、失焦、模态弹窗和目标退出，再声明其可控性已验收。

## 完整性底线

- 期望值来自需求、原始数据或独立计算，不能从被测输出倒推标准答案。
- 测试失败不能仅靠删断言、缩小输入或修改基准变成全绿。基准确已过期时，记录版本、来源与已确认规则，保留原差异，并补符合当前需求的检查；缩小范围后明确报告未覆盖部分。
- 启动成功、退出码为零、PNG 能生成或大量断言通过，都不能单独证明全部需求完成。视觉正确性、真实按钮事件、焦点、拖拽、DPI 和性能分别有对应验收标准。
- 流程能结束、每类资源曾出现，不等于完整组合符合原图；逐项核对应该出现的对象、数量、范围和应保留的部分。诊断证明原因不等于问题已修复。暂缓项保留在报告，不通过删分母变成“全部完成”。
- 只停止自己启动且身份已核对的测试进程；不关闭用户的应用或按进程名批量结束。关闭技能本身不代表已中断独立进程。
